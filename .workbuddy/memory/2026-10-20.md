## 账号按用途分池（v1.7）

**语义**：`Account.purposes: Vec<Purpose{chat,coding,vision,probe}>`，**空 = 不限用途**。设计成「收窄」而不是「切分」——不打标签的号什么活都接，打了才限定。这是兼容性红线：存量配置全无此字段，空若读成「都不能干」，升级即断网。`Account::admits()` 是唯一判定，路由与巡检共用。

**请求侧判定** `Purpose::infer(declared, has_image, from_agent)`，四顺位：
1. `x-freeport-purpose` 显式头（写错只 warn，不失败）
2. 含图 → vision
3. 已注入 Agent 的 key（`api_keys.name` 前缀 `agent:`）→ coding —— 零配置识别，这是整套机制的价值所在
4. 其余 → chat

**显式头是逃生舱**：带图的 coding 请求若显式写了 `coding`，就归 coding。第一顺位存在的意义就是「用户说了算」，不能因为和图片冲突就无视。

**过滤位置**：Gate 里 tombstone 之后、capability 之前，产出 `Rejected.kind="purpose"`。只过滤「谁能接」，不改权重与顺序——SWRR 与粘性完全不知道池的存在。`/v1/models` 与别名表不按池过滤（模型目录是能力声明，不是当前谁的额度可用）。

**可解释性**：503 文案点名「N 条凭据因用途标签被排除（本次请求按 X 处理）」，body 带 `purpose`；`GET /v1/route?purpose=` + `Gateway::explain_route_for()`；MCP `freeport_route` 加 `purpose` 参数、`freeport_quota` 输出 `purposes`。

**巡检**：`patrol::collect` **入队前**跳过「整家都没有 `admits(Probe)` 账号」的厂商——不能等发请求时再 continue，那样它每次被挑中、发现没账号、跳过，而 `overdue` 只增不减，永远排最前把别的模型饿死。巡挑选账号同样加 `admits`。代价：coding-only 号的模型健康度停在 unknown，UI 勾选时已提示。

**顺手修的既有 bug**：`has_any_key` 原来只查 `provider.id`（迁移期 account id == provider id 的遗留），新增凭据是 `acct_xxx` 时会把「有凭据」误报成「还没接入任何厂商」→ 改为任一账号有凭据。

**验证**：core 4 条分池单测 + model 4 条 Purpose 单测 + `tests/purpose_e2e.rs`（4 场景，桩上游抓 `Authorization` 断言哪把 key 真被发出）；workspace 全绿；`tsc --noEmit`；`vite build` 340KB / gzip 103KB。

**顺手修的两个既有 flake**（都是并行测试共享进程级状态）：
- `exts::tests` 两个用例各自 `set_var("FREEPORT_DATA_DIR")`，并行时互相覆盖目录 → 加模块级 `ENV_LOCK` 串行化（`extensions_dir()` 只解析一次那次的同类问题）
- `control::tests::tmpdir()` 用 `SystemTime` 纳秒做目录名，macOS 实际精度不够，两个用例偶尔撞到同一目录，一个 `remove_dir_all` 删掉另一个正在读的文件 → 改成进程内自增计数器

## 日志带上用途与判定依据（v1.7 补）

**改动**：`LogEntry` 加 `purpose`（`chat|coding|vision|probe`）与 `purposeSource`（`header|image|agent-key|default`）。核心是 `Purpose::infer_with_source()` —— 结果和依据**由同一次判定产出**，不给调用方各判一遍的机会（两处实现迟早会漂，然后日志写的依据和实际过滤用的池对不上，比不记更坏）。

## 又一次 exts flake，这次找到真因

`enable_with_permitted_domain_persists` 在全量并行下偶发失败（`find(id=="asr")` 拿到 None）。真因不是测试隔离，是**产品代码的并发洞**：`materialize_builtin()` 用 `std::fs::write(path, raw)` 直接覆盖，而 `installed()` 会并发读同一份 manifest —— 读者可能读到半截文件，验签失败后被 `continue` 跳过，这个扩展就从列表里**静默消失**。

修法：写 tmp + `rename`（原子），读者只会看到旧份或完整新份；失败时清掉 tmp。同时把 `exts::tests` 里两条不碰环境变量但也走 `ext_list()`（会往「当前」目录落 manifest）的用例也纳入 `ENV_LOCK`。测试断言改成 `expect("...缺了说明 manifest 没读出来")`，下次再出问题能直接看出是列表缺条目而不是配置没生效。

连续跑 4 次 `--lib`（86 tests）全绿。

## 摘要按用途池聚合 + 揪出「测试会写真实用户目录」的严重 bug

**摘要**：`Digest` 新增 `pools: Vec<PoolStat>`（purpose / requests / errors / okRate）与 `logScanned`。数据源是**内存日志环**（≤300 条），不是 24h 全量——所以界面标「最近 N 条请求」，MCP 在 `logScanned == 0` 时补一句 `poolHint`「空 ≠ 各池正常」。
两个刻意取舍：**零请求的池不输出**（不是 okRate:0，否则「从没被用过」看起来像「全挂」）；**失败过半且样本 ≥3** 才进 `attention`（一单失败是常态，阈值松了「需要处理」就成狼来了）。
`Gateway::digest()` 日志环为空时会先向活着的网关要日志（`inspect_live` → `/logs`），否则 MCP 进程永远报「今天没有请求」。
纯函数换成 `build_with_logs(data, now, &logs)`，`build()` 保留为不喂日志的兼容入口。

**顺手挖出的真 bug（严重）**：`a_second_instance_sees_the_live_memory_state...` 每跑一次都会往**真实** `~/Library/Application Support/dev.freeport.app/` 写一份测试配置。原因：`load_from(dir)` 只把 dir 记在 State 里给 `control.key` 用，而所有落盘都走 `store::save()` → 写进程级 `data_dir()`。请求路径上的 `persist_throttled`（配额/统计/健康度）就足够触发。沙箱恰好把 rename 挡了下来（留下一个比主文件新的 `freeport.json.tmp`），而 `load_best` **优先用更新的 tmp** —— 下一次启动就会把用户 20KB 的真配置换成 3KB 测试配置。已把残留 tmp 移到 `/tmp/fp-stray/` 备份。

**修法**：State 的 `dir` 改 `std::sync::RwLock`（落盘是同步、且在最热路径上），新增 `save_here(&Arc<State_>, &AppData)` 写**本实例目录**，33 处 `store::save(&d)` 全部改掉（server.rs / exts.rs / license.rs）。新增 `tests/store_target_e2e.rs`：把 `FREEPORT_DATA_DIR` 指向诱饵目录，`load_from(instance)` 后写两次，断言 **诱饵目录里没有 freeport.json**。

**验证**：workspace 全绿；mcp_e2e 11 条通过且真实目录不再出现 tmp；`tsc --noEmit`；`vite build` 342.6KB / gzip 103.6KB。

## 路由策略补齐 freellmapi 差距（极值策略）
- 对比 freellmapi 截图：其「手动/均衡/最智能/最快/最稳定 + 三维权重」；本项目已有 5 策略 + 命名链 + 实时候选链，缺单维度极值策略；用户选「只补极值策略、不做可调权重」
- `route.rs`：`Strategy` 五档→八档，新增 `Fastest`（探针 latency_ms 升序，没测过的垫底）/ `Stablest`（Healthy > Unknown/Probing > Degraded > Cooling，同档按 fails 升序、oks 降序）/ `Smartest`（实测 reasoning > tools > vision > 声明 context，实测覆盖声明的合并同能力门禁）；辅助函数 `health_of` / `smart_key`；parse 接受 fastest/stablest|stable/smartest，未知串仍回落 balanced
- 三个策略都是稳定排序纯重排，不写 SWRR `current`，与 balanced 互不污染
- 单测 ×3：`fastest_sorts_by_probe_latency` / `stablest_prefers_health_over_history` / `smartest_measured_beats_declared`（实测推翻声明后按上下文排）
- 前端：`bridge.ts` RouteStrategy 联合类型扩三值；`Routing.tsx` STRATEGIES 加最快/最稳定/最智能三卡；`GAP-ANALYSIS` 进度表第 5 行更新为八档

## 路由三维权重（可靠性 / 速度 / 智能）
- 需求来源：freellmapi 截图的「可靠性 70% · 速度 15% · 智能 15%」；上一轮只补了极值策略，用户明确「需要加」权重
- `model.rs`：新增 `RouteWeights{enabled,reliability,speed,intelligence}`（默认 70/15/15，`enabled=false`），挂在 `RoutingConfig.weights`，`is_unset()` 让未启用且默认时不落盘；`active()` 返回 `Option` 供调用点省 if
- `route.rs`：`blend_score` 按总和归一的加权合成；`health_factor` 抽出来单写（weight_factors 复用）；`speed_factor` 以 400ms 为半衰点、**没测过给 0.6**（给 1.0 会让「速度」权重反而先打未测通道）；`intelligence_factor` = 0.35 基座 + 推理 .30 + 工具 .12 + 视觉 .05 + 上下文 ≤.18（实测覆盖声明）
- 关键取舍：合成结果是乘在**档位 × 余量之后**的第三个因子，不替代它们——「该不该花」是产品判断，「两件都能花先花哪件」才是用户偏好
- `weight_of_model(p,account,model_id,ledger,health,now,weights)` 新增；`weight_of` 保留为 `weights=None` 的薄壳，老调用点零改动。`order()` 传 `data.routing.weights.active()`
- 网关：`set_routing` 收权重（夹 0..100，全 0 兜底 reliability=100 防止退化成纯轮转）；`/v1/route` 跳点新增 `factors.blend`（启用时出现），`weight` 改用 `weight_of_model`
- 前端：`GwWeights` 类型 + `RouteFactors.blend`；Routing 页「策略与命名链」卡内加 `WeightsRow`（开关 + 三滑杆 + 数字框 + 归一百分比，滑杆松手/数字失焦才提交，避免拖动时刷盘）；HopRow 第三因子在启用时显示 `score` 而非 `health`
- 单测：core `custom_weights_flip_the_winner`（70/15/15 选稳的，10/45/45 选快的）、`disabled_weights_keep_the_legacy_formula`；gateway 新增 `tests/weights_e2e.rs` 端到端（未启用→slow 先、可靠性 70→slow、速度 100→fast、重启后仍生效、关掉回旧公式且 blend 消失）
- 验证：全 workspace 0 失败（56 集）、tsc 干净、vite build 407KB
